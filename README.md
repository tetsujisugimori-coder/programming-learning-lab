# プログラム学習 | Programming Learning Lab

**プログラミングを学びながら、インタラクティブな学習表現を研究し、自分自身の理解を深め続けるプロジェクト。**

Python・Shell（PowerShell / Bash）・TypeScriptを主な題材とし、コードを読んで終わるのではなく、**予想する → 操作する → 実行する → 結果を確かめる → 修正する → 応用する**という体験を重視します。

本リポジトリは完成期限や最終的な「全編完結」を設けない、**継続更新型の学習・研究の場**です。まず基本編を整え、その後も新機能、珍しいコマンド、実務的な課題、ケーススタディ、「こんなこともできる」という発見を応用編へ随時追加していきます。

> **現在の段階：Python基本編の教材基盤・第1章を実装。** 第2〜13章は目標一覧と「準備中」の表示のみです。以下の長期構想と、今回の実装範囲を区別します。

## サイトを動かす

Node.js 24 LTSを推奨します。教材の実行確認には手元のPythonを使います。

```powershell
npm ci
npm run dev
```

表示されたローカルURLを開きます。Pythonコードはブラウザー内では実行しません。学習者はWindows + VS Code + Python本体 + Microsoft製Python拡張 + PowerShellを使います。

```powershell
npm run check
node tools/verify-python.mjs
npx playwright install chromium webkit
npm run test:e2e
```

`check` はlint・型検査・教材構造検査・静的buildです。Pythonコード検証は固定教材だけを実行し、学習者の入力を実行しません。ブラウザー検査は専用サーバーを空きポートで起動・終了し、既存サーバーを再利用しません。先に `npm run build` を行ってください。Linuxでのブラウザー準備は `npx playwright install --with-deps chromium webkit`。

`npm run build` で `dist/` を生成し、`npm run preview -- --port 43872` で確認できます。公開先は未設定（着手時GitHub Pagesは404）。`dist/` を静的ホストの配信対象にでき、相対アセットURLなのでサブパスにも配置できます。本PRで公開・自動デプロイは行いません。GitHub Actionsは検査と証拠artifactのみです。

## 1. プロジェクトの3つの目的

### 1.1 プログラミングの学習

- Python、PowerShell / Bash、TypeScriptの基本文法、処理の仕組み、実行環境、設計の考え方を学ぶ。
- ファイル操作、データ処理、自動化、Webアプリ開発、AI支援開発など実践的な題材へ進む。
- 成功例だけでなく、エラーの意味、原因の調べ方、修正の手順を扱う。

### 1.2 インタラクティブな表現の研究

- コードの実行結果、変数の変化、処理の流れ、コマンドの作用を、操作・図解・アニメーション・シミュレーションなどで表現する。
- エディタ、ターミナル、比較表示、ヒント、可視化など、理解を助けるUIを試作する。
- 見た目の面白さだけでなく、**その表現によって何が理解しやすくなったか**を検証する。

### 1.3 自分自身の学習と技術習得

- 教材を設計・制作・試用する過程を、自身の学習として扱う。
- AIに実装を支援してもらう場合も、設計判断、コードの構造、実行結果、制約を説明・検証できることを重視する。
- 教材の完成度と自分の理解度は別々に振り返り、理解が足りない部分を次の学習課題にする。

**教材制作は目的ではなく、学習と表現研究のための手段でもある**という考え方を基本にします。

## 3. 言語別の学習領域

### 3.1 Python

**基本編の候補**

- 実行環境、式、変数、型、入出力
- 条件分岐、繰り返し、関数、コレクション
- ファイル操作、例外処理、モジュール、デバッグ
- 小さなプログラムの設計とテスト

**応用編の候補**

- CSV / JSONなどのデータ処理、ファイル整理、自動化
- APIの利用、可視化、外部ライブラリ
- 実務的な小ツールやケーススタディ
- 他言語・他ツールとの処理方法の比較

### 3.2 Shell（PowerShell / Bash）

**基本編の候補**

- ターミナルとは何か、コマンドの構造とヘルプの読み方
- パス、ファイル、フォルダ、環境変数、入出力
- パイプライン、条件分岐、繰り返し、スクリプト
- PowerShellとBashの違い、コマンド実行時の注意点
- Git / GitHubの基本操作と変更差分の確認

**AI CLI・開発ツールも学習対象に含めます。**

- **Codex CLI**：AIとの対話、コード調査、変更提案、実装、差分確認、テスト
- **Ollama**：ローカルLLMの導入、モデル管理、実行、API利用、制約の理解
- **OpenCode**：AIコーディング環境の操作、利用するモデルや実行方式の比較
- **MCP / Skillsなど**：外部ツール連携、自動化、操作権限、設定の調査

AIツールの利用は「使い方の暗記」で終えず、**裏側のShell操作・ファイル変更・実行権限・安全性**も合わせて学びます。ツール名や仕様は変わり得るため、教材ごとに検証日・バージョン・環境を記録します。

**応用編の候補**

- あまり使わないが便利なコマンドやオプション
- 複数ファイルの一括処理、ログ調査、環境診断
- Gitの問題調査と復旧のケーススタディ
- Codex CLI・OpenCode・Ollamaの比較実験
- AIツールが提案した変更を人間が検証する演習

### 3.3 TypeScript

**基本編の候補**

**応用編の候補**

- インタラクティブUIと状態管理

- コードの変更が画面にどう反映されるかの可視化

※各項目は初期候補です。実際の章立て・順番・範囲は、制作と学習の結果に応じて見直します。

## 4. 教材の基本的な学習体験

各レッスンは、題材に応じて次のサイクルを組み込みます。

1. **考える**：何が起きるか予想し、前提を確認する。
2. **操作する**：コードやコマンド、入力値を自分で変更する。
3. **実行する**：実際の実行環境、または明示された模擬環境で結果を得る。
4. **比較する**：予想と実行結果、変更前と変更後を比較する。
5. **理解する**：なぜそうなったか、エラーの原因は何かを説明する。
6. **再挑戦・応用する**：条件を変えて試し、小さな課題へ発展させる。

完成した答えを初めから示すだけでなく、段階的なヒントと、学習者が自分で判断できる余地を用意します。必要に応じて理解度チェックや学習メモも扱います。

### インタラクティブ表現の例

- 変数・配列・処理順序の変化を段階表示する。
- コードエディタと実行結果を並べて比較する。
- コマンドが模擬ファイルシステムに与える影響を視覚化する。
- AI CLIの指示、ツール呼び出し、承認、ファイル差分、テスト結果を追跡する。
- 失敗例、原因、修正後の違いを操作して確かめる。

## 5. 実行環境と安全性

言語ごとに実行可能な範囲が異なるため、**本物の実行と模擬体験を混同しません**。

- **Python**：ブラウザ内実行（例：Pyodide）などを候補として検討する。
- **TypeScript**：ブラウザでの型検査・変換と、隔離されたコード実行を検討する。
- **Shell**：まず模擬ファイルシステムや安全な演習で学び、実環境操作との違いを明記する。実際のPowerShell / BashやAI CLIの演習は、専用の作業領域と明示的な確認のもとで行う。

特にAI CLI・Shellについては、次を重視します。

- 読み取り、書き込み、削除、ネットワーク送信、外部コマンド実行を区別する。
- 危険なコマンドは、いきなり実行せず影響範囲・対象・復旧方法を確かめる。
- APIキー、トークン、認証情報、個人データを教材のログや公開成果物に含めない。
- AIの「変更した」「成功した」という報告だけで判断せず、差分・実行結果・テストで確認する。
- クラウドAIとローカルLLMを区別し、外部送信の有無・モデル・利用環境を明示する。
- ブラウザ上のデモを、OSや実ファイルへの無制限な操作権限と誤解させない。

## 6. 応用編の継続的な追加方針

応用編は体系的な教科書というより、**辞典・実験ノート・ケーススタディ集**として成長させます。

主な追加対象：

- ツールや言語の新機能・仕様変更
- 普段は使わないコマンド、便利なオプション、意外な使い道
- 実際に遭遇したエラー、原因調査、復旧事例
- 同じ目的を別の言語・ツール・AIで達成する比較
- 「こんなこともできる」と感じた機能や表現の実験

各記事には、できる範囲で以下の情報を持たせます。

| 項目 | 記録する内容 |
| --- | --- |
| 対象 | 言語・コマンド・ツール・機能 |
| 難易度・前提 | 必要な基本編の知識、事前準備 |
| 学習目標 | 何ができるようになるか |
| 実行環境 | OS、ランタイム、ツール・モデルのバージョン、確認日 |
| 体験内容 | 予想・実行・観察・変更・応用 |
| 確認結果 | 実測した内容、未確認事項、再現条件 |
| 注意点 | 制限、安全性、環境依存、既知の問題 |
| 関連記事 | 基本編・関連応用編・研究室へのリンク |

後から古くなった記事を更新した場合も、何が変わったのか分かるようにします。

## 7. インタラクティブ研究室

学習表現の改善を独立した研究課題として扱います。例えば「アニメーションを付けると理解しやすくなるか」「エラーを段階的に見せると修正できるか」「AIツールの実行過程を可視化すると判断しやすくなるか」を調べます。

研究は、**問い → 仮説 → 試作 → 操作・観察 → 比較 → 振り返り**を基本にします。表現が面白くても理解を助けない場合は、その点も結果として残します。

PCでは教材・エディタ・実行結果の並列表示、スマートフォンでは狭い画面でも学べる操作・切替表示を検討します。アクセシビリティ、キーボード操作、エラー表示、学習履歴の扱いも研究対象とします。

## 9. 開発・検証の進め方

1. 基本編と研究室の共通要件を整理する。
2. 小さな教材を試作し、学習体験と実装方式を検証する。
3. 学習目標、操作方法、実行結果、エラーの扱いを確認する。
4. 必要に応じてIssue → ブランチ → 実装 → Draft PR → テスト → 独立レビュー → マージで管理する。
5. 重大な不具合は修正し、軽微な課題や発展案も記録して次の改善へつなげる。
6. 基本編の拡充、応用編の記事追加、研究室の実験を継続する。

確認項目はコードが動くことだけではありません。

- **技術的な正しさ**：実行結果・テスト・環境条件が正しいか。
- **学習しやすさ**：理解に必要な前提・操作・ヒント・説明があるか。
- **表現研究の成果**：可視化やインタラクションが理解にどう役立ったか。
- **自身の理解**：仕組み、制約、実装判断を説明・再現できるか。
